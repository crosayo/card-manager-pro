### 1.1 層の役割

| 層 | 役割 | 規約 |
|---|---|---|
| `app/*/page.tsx` | 画面の状態（データ取得・更新処理）を持つ | DBへは必ず `api` 経由 |
| `views/*` | 表示とユーザー操作 | 共有状態は `useAppContext()` |
| `services/api.ts` | DB操作、snake_case ↔ camelCase の変換、エラー変換 | 失敗は `handleSupabaseError` で例外化する。**握りつぶさない** |
| DB関数（RPC） | 複数テーブルの更新、権限チェック、アトミックな加算 | 定義は `supabase/schema.sql` に集約 |

### 2.2 エラー処理

| 関数 | 用途 |
|---|---|
| `handleSupabaseError(error, action)` | Supabaseのエラーを `Error`（`code` / `details` 付き）に変換して投げる。`42501` や RLS違反は「権限エラー」の文言に変換 |
| `isMissingFunction(error)` | RPC未登録の判定（`42883` または `PGRST202`）。未登録時のみフォールバック処理へ |
| `throwIfAnyFailed(results, action)` | 複数件の更新結果のうち1件でも失敗があれば例外化 |

主なエラーコード: `42P01`（テーブルなし）、`42883` / `PGRST202`（関数なし）、`42501`（権限なし）、`22023`（DB関数内の入力エラー。メッセージは日本語で利用者に表示可能）、`PGRST116`（該当行なし）。

画面側はトースト（`addToast`）で通知する。エラー詳細（`AppError`）を渡すとトーストからコピーできる。

### 3.2 DB関数・トリガー

| 名前 | 種別 | 権限 | 処理 |
|---|---|---|---|
| `request_invite_code()` | SQL / stable | — | リクエストヘッダー `x-invite-code` の値（`current_setting('request.headers')`） |
| `is_admin()` | SQL / definer / stable（`search_path = public, pg_temp`） | 全員（anon は常に false） | `auth.uid()` が `admins` 表にあれば true。書き込みポリシー・管理者用DB関数・`/api/scrape`・画面の `isAdmin` が使う（Q-2026-11-06-1） |
| `can_view()` | SQL / definer | — | 管理者（`is_admin()`）または有効期限内・未取消の招待コードなら true。閲覧ポリシーとDB関数の入口チェックで使用 |
| `request_client_ip()` | SQL / stable | — | リクエスト元のIPアドレス（前段プロキシのヘッダーから） |
| `redeem_invite(p_code)` | definer | 全員 | 招待コードの確認。有効なら最終アクセス・回数を更新、自動延長、アクセス履歴を記録し `{valid, label, expires_at}` を返す |
| `normalize_search(text)` | SQL / immutable | — | NFKC → 空白・記号除去 → ひらがな→カタカナ → 小文字化（§5） |
| `search_items(...)` | plpgsql / invoker | 全員 | 検索・絞込・並替・ページング。戻り値 `{data, count}` |
| `increment_stock(item_id, delta)` | definer | **管理者のみ**（関数内で `is_admin()`＋anon実行権限なし） | 在庫を `greatest(0, stock+delta)` でアトミック更新 |
| `increment_supply_stock(p_supply_id, p_delta)` | invoker | RLSに従う | サプライ在庫のアトミック更新 |
| `reset_all_data()` | definer | **管理者のみ**（`is_admin()`） | items / products / news を全削除（`truncate … cascade`）。**items を外部キーで参照する `request_items`・`stock_logs` も全件消える**（サプライの明細・ログも含む。リクエスト本体・編集履歴・サプライ・招待リンクは残る）。設定画面の実行前の警告にも明記（Q-2026-11-06-4） |
| `get_dashboard_stats()` / `get_distinct_rarities()` | definer（`search_path = public, pg_temp`。Q-2026-11-06-6） | 全員（読み取りのみ。入口で `can_view()`） | 集計 |
| `create_request(name, message, items jsonb)` | definer | 全員 | 本体＋明細を1トランザクションで登録し `{id, token}` を返す。登録前に在庫の上限（B7）と入力の上限（名前50文字・メモ1000文字・明細200件、各明細は item_id と supply_id のどちらか一方だけ。Q-2026-11-06-3）を確かめる |
| `resolve_request_token(token)` | definer | 全員 | 受付中のリクエストIDを返す（無効・処理済みは null） |
| `edit_request_by_token(token, message, item_changes, remove_item_ids)` | definer | 全員（トークン照合） | メモ・枚数変更・明細削除と編集履歴の記録。全件削除は不可。メモ1000文字・枚数変更と削除は各200件まで（Q-2026-11-06-3） |
| `swap_request_item_by_token(token, request_item_id, new_item_id)` | definer | 全員（トークン照合） | 同名カードの別バリアントへ差し替え |
| `change_request_item_as_admin(request_item_id, new_item_id, quantity)` | definer（`search_path = public, pg_temp`） | **管理者のみ**（`is_admin()`＋anon実行権限なし） | 管理者のカード変更（D8）。同名カードの別型番・別レアリティへの差し替えと枚数変更、編集履歴（`カード変更`・`数量`）、完了済みなら在庫の差分（`greatest(0, …)`）と在庫ログ（`source='request'`・`note='完了済みリクエストの編集'`）を1つのトランザクションで行う（Q-2026-11-06-5） |
| `handle_updated_at()` | トリガー | — | items の updated_at 更新 |
| `rotate_request_token_on_resolve()` | トリガー（`on_request_resolved`） | — | status が pending から変わったら token を入れ替え |
| `fetch_items_by_release_date(...)` | 旧関数 | — | **未使用**。`search_items` に置き換え済み。削除してよい |

> `definer`（SECURITY DEFINER）関数はRLSを迂回するため、**必ず関数内で権限・入力を検証すること**。新規追加時は `set search_path = public` を付ける。

## 4. セキュリティ設計

### 4.1 テーブル権限（2026-10-30 時点）

「招待あり」= リクエストヘッダー `x-invite-code` に有効な招待コードがある場合（`can_view()`）。

「管理者」= `admins` 表に登録された Auth ユーザー（`is_admin()`）。2026-11-14（Q-2026-11-06-1）から、書き込みポリシーと管理者用DB関数の条件は `auth.role() = 'authenticated'`（ログインしているだけ）ではなく `(select public.is_admin())`。ログインしていても admins にないユーザーは、招待なしの未ログインと同じ扱い（何も見えない・書けない）。

| テーブル | 未ログイン・招待あり | 未ログイン・招待なし | 管理者（`is_admin()`） |
|---|---|---|---|
| items / products / news / config / supplies | 閲覧のみ | **何も見えない**（0件） | 全操作 |
| requests | **列単位で閲覧のみ**（`token`・`admin_memo` 列は閲覧不可。`admin_memo` は 2026-11-14 の Q-2026-11-06-2 から）。書き込み不可 | 何も見えない | 全操作 |
| request_items / request_edit_logs | 閲覧のみ。書き込み不可 | 何も見えない | 全操作 |
| stock_logs | 不可 | 不可 | 全操作 |
| invites | 不可 | 不可 | 全操作 |

- requests / request_items / request_edit_logs の INSERT ポリシーは「Allow authenticated insert」（authenticated のみ）。旧「Allow public insert」（public・条件なし）は 2026-11-01 に置き換え（`リクエスト挿入ポリシー変更_2026-11-01.sql`。実行は [03](03_改修ログ.md) で確認）。anon にはこの3表の INSERT 権限もない。
- request_items / request_edit_logs の DELETE ポリシーは「Allow authenticated delete」（authenticated のみ。2026-11-01 追加、`リクエスト削除ポリシー追加_2026-11-01.sql`）。それまでは DELETE ポリシーがなく、管理者の編集で明細を外す操作（`editRequestAsAdmin` の `itemsToRemove`）が RLS で0件になりエラーになっていた。requests の削除は「Authenticated users can delete requests」で、明細・履歴は外部キーの ON DELETE CASCADE で消える。
- 匿名で呼べるDB関数（`get_dashboard_stats` / `get_distinct_rarities` / `create_request` / `resolve_request_token` / `edit_request_by_token` / `swap_request_item_by_token`）も、入口で `can_view()` を確認する。`search_items` は invoker なのでRLSにより招待なしでは0件。

### 4.1.1 招待制の仕組み
1. 管理者が `/invites` で招待リンク `https://…/#invite=コード` を発行する。コードは URL の fragment（`#`）で渡すため、サーバー（Vercel のアクセスログ）には送られない（2026-11-14 Q-2026-11-06-7。それまでの `?invite=コード` のリンクもそのまま使える）。
2. 閲覧者が開くと、`lib/supabase.ts` のクライアント生成時（最初の通信より前）に `captureInviteFromUrl` がコードを localStorage（`card-manager:invite`）へ保存し、`history.replaceState` で URL（fragment・query の両方）から除去する（`lib/urlSecret.ts` の `takeSecretParam`）。
3. Supabase への全通信に、独自の `fetch` で `x-invite-code` ヘッダーを付ける（Supabase の CORS はこのヘッダーを許可していることを確認済み）。
4. 起動時に `redeem_invite` で状態を確認し、`AppShell` が「招待リンクが必要です」画面と通常画面を出し分ける。期限が来たら閲覧中でも閲覧不可に切り替わる。
5. `redeem_invite` が未登録（SQL未適用）の環境では、招待制は未導入として従来どおり公開扱いにする。

- 申請者の書き込みは DB関数（`create_request` / `edit_request_by_token` / `swap_request_item_by_token`）経由のみ。
- `requests` を anon で `select=*` すると権限エラーになるため、アプリは列を明示して取得する（`api.ts` の `REQUEST_PUBLIC_COLUMNS`。`token`・`admin_memo` は管理者のときだけ `REQUEST_ADMIN_COLUMNS` で足す。`fetchRequests` / `fetchRequestById` の `asAdmin`）。

### 4.2 既知の注意点
- `config` は全員が閲覧できるため、**Discord Webhook URL も第三者から読める**（オーナー判断で現状維持）。
- Discord 通知（`api.sendDiscordNotification`）は申請者の名前・メモをそのまま本文に入れるため、`allowed_mentions: { parse: [] }` を付けて `@everyone`・`@here`・ユーザー／ロールのメンションを無効にしている（Q-2026-11-06-6）。

### 4.3 サーバー側API（`/api/scrape`）の保護
| 対策 | 内容 |
|---|---|
| 認証 | `Authorization: Bearer <アクセストークン>` を Supabase Auth（`auth.getUser`）で検証。未ログイン・期限切れは 401 |
| 管理者の確認 | 同じトークンで DB関数 `is_admin` を呼び、true でなければ 403、確認できなければ 503（Q-2026-11-06-1） |
| 取得先の制限 | `ALLOWED_HOSTS`（`yugioh-wiki.net` とそのサブドメイン）の http(s) のみ。ポート指定・認証情報付きURLは拒否 |
| リダイレクト | 自動追従せず（`redirect: 'manual'`）、最大3回まで転送先を毎回検査。許可外へ転送されたら中止 |
| 時間とサイズの上限 | 取得全体（リダイレクト・本文の読み込みを含む）を `AbortSignal.timeout(15秒)` で打ち切り 504。本文は 5MB まで（`lib/fetchLimit.ts` の `readBodyWithLimit`。Content-Length か読んだ量が超えたら中止）で 413（Q-2026-11-06-6） |
| エラーの返し方 | 例外の内容はサーバーのログ（`console.error`）にだけ残し、応答は一般的な文言（500）。取得先の HTTP エラーは状態コードだけ返す（502） |
| HTML の解析 | 行・セル・リスト・リンクの中身は `lib/htmlElements.ts` の `extractElementContents` で取り出す。閉じタグがなくても入力の長さに比例した時間で終わる（以前の正規表現は2乗で遅くなった） |

取得先を増やす場合は `route.ts` の `ALLOWED_HOSTS` に追加する。

### 4.4 セキュリティヘッダー（`next.config.ts` の `headers()`）

全ページ（`/:path*`）に次の3つを付ける（2026-11-14, T-2026-11-14-C）。

| ヘッダー | 値 | 目的 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | ブラウザに Content-Type を推測させない |
| `Content-Security-Policy` | `frame-ancestors 'none'` | 他サイトの iframe への埋め込みを禁止（クリックジャッキング対策） |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 外部サイトへはオリジンだけを送り、編集用リンクのトークンなどを含む URL を渡さない |

`script-src` などの細かい CSP は、Supabase への接続や Next.js のインライン script を壊しやすいため入れていない。入れる場合はプレビューで招待リンクの閲覧・リクエスト送信・サプライ画像（Supabase Storage）を確かめてから。

## 5. 検索仕様

### 5.1 正規化規則（DB `normalize_search` と `utils.ts` の `toSearchKey` は同一規則）
1. Unicode NFKC 正規化（全角英数・半角カナ → 標準形）
2. 空白・ASCII記号・カード名に使われる記号（`《》「」『』【】・〈〉〔〕［］｛｝、。～〜―‐–—−･·☆★♪♡〝〟…`）を除去
3. ひらがな → カタカナ（`ぁ`〜`ゖ` を +0x60）
4. 小文字化

### 5.2 照合
- 検索ワードを空白（全角含む）で分割し、各語を正規化 → **すべての語が `search_key` に含まれる行**（AND検索）。
- `search_key` は「名前|型番|パック名」を `|` で連結しているため、語が項目をまたいで一致することはない。
- 例: 「ブラック マジシャン」「ぶらっくまじしゃん」「E-HERO」「dbss-jp036」「青眼 SM51」

### 5.3 並び替え（`p_sort_key`）
`releaseDate`（パックの発売日）/ `cardId` / `name` / `rarity`（`config.rarities` の順）/ `category` / `stock` / `updatedAt`、未指定は ID 降順。同順位は 型番 → レアリティ順 → ID。

### 5.4 変更時の注意
- 規則を変える場合は **DB関数と `toSearchKey` の両方**を変更し、`update public.items set name = name;` で全行の `search_key` を再計算する。
- 保存用の `normalizeForStorage` はひらがなを変換しない。**比較用の変換を保存経路で使わないこと**（過去にカード名をカタカナ化して壊した不具合の原因）。

## 6. 処理フロー

### 6.1 在庫の増減（連打対応）
1. 画面で即座に表示を更新し、増減数を `pendingDeltaRef` に積む。
2. 100ms 待って積み上がった増減数をまとめて `increment_stock` で送信。
3. 応答を待つ間のクリック分を加算して表示に反映（巻き戻り防止）。失敗時はサーバーから現在値を取り直す。
4. `stock_logs` に記録（失敗しても在庫操作は成功扱い）。

サプライも同じ方式（`increment_supply_stock`）。

### 6.2 リクエストのライフサイクル

```
[ゲスト] カートに追加 → 送信 ──create_request──▶ requests(pending) + request_items
                         ◀── {id, token}
          完了画面に編集用リンク /requests#token=… を表示・コピーを促す（以前の /requests?token=… も読める）
          トークンを localStorage（card-manager:request-tokens）に保存

[ゲスト] 編集用リンクを開く ──resolve_request_token──▶ 受付中ならID（ブラウザに保存。トークンは照合の前に URL から除去）
          編集 ──edit_request_by_token / swap_request_item_by_token──▶ 更新＋編集履歴

[管理者] 完了 ──requests.status=completed──▶ トリガーで token 入れ替え（申請者のリンクは無効）
          ※ 完了・キャンセルは status=pending の行だけ更新する。別タブ等で先に処理済みなら「すでに処理済み」で止め、在庫を二重に減らさない（2026-11-01）
          明細ごとに在庫を減算（カード: increment_stock / サプライ: increment_supply_stock）＋ stock_logs
[管理者] キャンセル ──status=cancelled──▶ token 入れ替え（在庫は変えない）
[管理者] 編集 → 明細の「変更」 ──▶ 変更先（同名の別型番・別レアリティ）と枚数を選んで即保存（`RequestsView` の `applyChange` → DB関数 `change_request_item_as_admin`。完了済みなら在庫の差分も同じトランザクションで反映。在庫は「在庫 / 他で受付中」を表示）
[管理者] 完了済みを編集 ──▶ 枚数差分・削除分・差し替え分を在庫へ戻す/減らす（note: 完了済みリクエストの編集）
```

在庫一覧には「受付中リクエストの枚数」（`fetchPendingQuantities`）を表示し、カートに入れられる上限は「在庫 − 受付中枚数」（サプライは在庫数。[05](05_改善提案とロードマップ.md) B8）。送信時にも DB 関数 `create_request` が同じ上限（カードは「在庫 − 受付中枚数」、サプライは在庫数）を確かめ、超えていれば「在庫が足りません: カード名 （リクエストできるのは残り N枚）」で送信全体を取り消す（B7。対象の items・supplies 行を id 順に `FOR UPDATE` でロックしてから数えるため、同時送信でも上限を超えない）。画面はカートを残したまま、枚数を減らして送り直す案内を出す（`CartFloat.tsx`）。リクエストの編集（`edit_request_by_token`）で枚数を増やす場合は確かめていない。「リクエスト」ボタンは個数選択ダイアログを開き、カートに入っていればその枚数で開いて変更する（`useQuantityDialog`）。

### 6.3 CSV在庫上書き
1. ヘッダー行から `ID` と `在庫数` の列位置を特定（列順に依存しない）。
2. 在庫数が0以上の整数でない行（マイナス・小数・文字）は「不正な値」として除く。同じIDが複数行あれば最後の行を使う（2026-11-01）。
3. 対象IDの現在在庫を取得し、変更がある行だけ更新。
4. 結果を「更新／変更なし／該当IDなし／不正な値／失敗」の件数で表示し、更新した行のみ増減数を `stock_logs`（source=csv）へ記録。

### 6.4 Wiki取込
1. 画面がログイン中のアクセストークンを付けて `/api/scrape` を呼ぶ。サーバーはトークン・管理者かどうか・URLを検証し（§4.3）、HTMLを取得する（15秒・5MB まで。文字コードは Content-Type、なければ EUC-JP）。
2. 本文領域の表、なければリストから「型番・カード名・レアリティ」を抽出。複数レアリティは行を分ける。
   - 型番は `lib/cardId.ts` の `CARD_ID_RE`（`/\b((?=[0-9]*[A-Z])[A-Z0-9]+-JP(?:\d{3,4}|[A-Z]\d{2,3}))\b/`）。英字を1文字以上含む英数字＋`-JP`＋数字3〜4桁、または英字1文字＋数字2〜3桁。`26LP-JP001` のような数字始まり（2026-11-03 `336c83c`）、`IMPH-JPS01`（＋1パック）・`IMPH-JPT01`（トークン）のように JP の後に英字が入るもの（2026-11-03 `7cbc8be`）も拾う。単体テスト `cardId.test.ts`。
   - レアリティは `lib/rarity.ts` の `normalizeRarity`。`COMPOUND_RARITY_PATTERNS` の26パターン（日本語名・英語名。長い名前を先に判定し、一致した部分は除く）でコードにし、残りの「ノーマル／N」「レア／R」を足す。何も当たらなければ `N`。主な対応: クォーターセンチュリーシークレットレア・25th Secret Rare → `QCSE`、プリズマティックシークレットレア → `PSE`、エクストラシークレットレア → `EXSE`、20th・10000 シークレットレア → `20thSE`・`10000SE`、ゴールドシークレットレア → `GSE`、プレミアムゴールドレア → `PG`、グランドマスターレア → `GMR`、ミレニアム（シークレット・ウルトラ・スーパー・レア）→ `M+SE`・`M+UR`・`M+SR`・`M`、KCウルトラレア → `KC+UR`、シークレット・ウルトラ・スーパー・ホログラフィックパラレルレア → `P+SE`・`P+UR`・`P+SR`・`P+HR`、ホログラフィックレア → `HR`、コレクターズレア → `CR`、ゴールドレア → `GR`、アルティメットレア → `UL`、シークレット・ウルトラ・スーパーレア → `SE`・`UR`・`SR`、ノーマルパラレル → `P`、ノーマルレア → `NR`。表は単体テスト `rarity.test.ts` と合わせて直す。デザイン違い（`UR-初期` など）と Ver. 違いは Wiki 取込では判定しない（登録後に手で直す）。
3. 登録先パック: 取り込んだパック名（見出し。なければ型番の頭）と同じ名前の既存パックがあればそれを選ぶ。なければ、取り込んだ行でいちばん多い型番の頭（セットコード。`lib/packMatch.ts`）で既存の items を探し（`api.fetchCategoriesBySetCode`、`card_id ilike '<コード>-JP%'`、2,000行まで）、行数のいちばん多い既存パックを初期選択にして注意書き（ほかの候補も表示）を出す。自動では確定せず、管理者が選び直すか「新しいパックを作成」に切り替えられる（パック名には見出しが入っている）。どれも見つからなければ従来どおり新規パック（2026-11-14。一括登録で作ったパック名が Wiki の見出しと一致しないことによる二重登録を防ぐ）。
4. 画面で内容を編集し、既存カードと重複する場合は「在庫を加算／上書き／スキップ」を選んで登録。

| 変数 | 用途 | 設定場所 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase プロジェクトURL | `.env.local` / Vercel の Environment Variables |

- `service_role` キーはアプリに置かないこと（RLSを完全に迂回できるため）。

## 9. コーディング規約（現行コードに合わせる）
- UI文言・コメント・コミットメッセージは日本語。
- TypeScript は camelCase、DB は snake_case。変換は `api.ts` の `mapDb…` 関数で行う。
- DBの失敗は握りつぶさず、利用者に分かる文言でトースト表示する。
- 改行コードは Git の `core.autocrlf=true`（作業ツリーは CRLF）。一括置換スクリプトを使う場合は改行コードに注意。
- `catch` では `e: any` を使わず `catch (e)` とし、メッセージ・コードは `utils.ts` の `getErrorMessage`・`getErrorCode` で取り出す。
- `npm run lint` はエラー・警告とも0件を保つ。`eslint-disable` は理由を書いた `eslint-disable-next-line` の行単位に限り、新たに増やすときは相談する（現状は `react-hooks/set-state-in-effect` 6か所と `@next/next/no-img-element` 3か所）。
- コミット前に `npm run build`・`npm run lint`・`npx tsc --noEmit` が通ることを確認する。
- 画面の見た目の基準（2026-11-01, D4。Tailwind UI などの管理画面の定番にならう）:
  - 外枠は `components/layout/Page.tsx` の `PageContainer`（`p-4 md:p-8 pb-24 max-w-7xl mx-auto`）。フォーム中心のページ（招待リンク・製品マスタ・システム設定）は `narrow` で枠の中を幅 4xl・左寄せにする。どのページでも見出しの左端の位置は同じ。
  - ページ見出しは `PageHeader`（`text-2xl font-bold text-slate-800`、アイコン24・`text-cyan-600`、説明は `text-sm text-slate-500`、右側に操作ボタン）。各ページで h2 を直接書かない。
  - 節・カード・ダイアログの見出しは `text-lg font-bold text-slate-800`。本文・表のセル・ボタン・入力欄は `text-sm`、補足は `text-xs text-slate-500`。
  - 表の見出し行は `bg-slate-50 border-b border-slate-200 text-xs font-bold text-slate-500`。
  - 印刷: サイドバー・スマホ用ヘッダー・カート・トーストは `print:hidden`、本文は `print:!ml-0`。画面ごとに印刷で隠すものは `print:hidden` を付ける（ピッキングリスト）。
  - 例外: ログイン画面・招待リンクが必要な画面は中央のカード表示。ダッシュボードの集計値・導線の大きな文字は意図的に大きくしている。
