## 3. 複数人の在庫を管理できるツールへの成長

### 3.1 現状の制約

| 制約 | 理由 |
|---|---|
| オーナーは1人だけ | 全データが「1つの在庫」前提で、どの行が誰のものかを持っていない |
| ログイン＝全権限 | ロールの概念がない。管理者を増やすと全員が全データを削除できる |
| カード情報と在庫が同じ行 | 同じカード（名前・型番・レアリティ）の情報を、オーナーごとに重複して持つことになる |
| 設定が全体で1つ | レアリティ順・Discord通知などがオーナーごとに持てない |

### 3.2 段階的な拡張案

| 段階 | 目標 | 主な変更 | 規模 |
|---|---|---|---|
| **段階0**（現状） | 1人のオーナーが在庫を公開 | — | — |
| **段階1** | 共同管理（家族・仲間内で1つの在庫を管理） | `profiles` と役割（オーナー／編集者／閲覧者）、RLSを役割で判定、操作ログに `user_id` | 中 |
| **段階2** | 複数オーナー（各自が自分の在庫を持ち、公開ページを持つ） | 「ショップ（在庫の持ち主）」の導入、カード情報の共通化、全テーブルに `shop_id`、公開URL `/s/{ショップ名}` | 大 |
| **段階3** | 公開サービス化（誰でも登録して使える） | サインアップ、利用規約・プライバシーポリシー、利用量の上限、必要なら課金 | 大 |

### 3.3 段階2のデータ設計案

最も効果が大きいのは、**カード情報（共通のカタログ）と、各オーナーの在庫を分けること**。Wiki取込は1回だけ行えば全員が使え、各オーナーは在庫数だけを持てばよくなる。

```
cards（共通カタログ。管理者が取込）          shops（在庫の持ち主）
  id, name, card_id, rarity, product_id        id, slug, display_name, settings(jsonb)
           │                                        │
           └──────────┬─────────────────────────────┘
                      ▼
               inventories（各ショップの在庫）
                 shop_id, card_id(FK→cards), stock, location, updated_at

shop_members（ショップの利用者と役割）         requests / supplies / stock_logs / news
  shop_id, user_id, role(owner/editor/viewer)    → すべてに shop_id を追加
```

- **RLS**: 「自分がメンバーのショップの行だけ書き込める」を全テーブルで共通の関数（例: `is_shop_member(shop_id, role)`）で判定する。
- **公開ページ**: 閲覧は `shops.is_public` のショップだけ。リクエストはショップ単位で受け付ける。
- **検索**: `search_key` は `cards` に持ち、`search_items` に `p_shop_id` を追加。
- **既存データの移行**: 既存の全行を「既定のショップ（現オーナー）」に割り当てる。`items` を `cards` と `inventories` に分割する移行SQLを用意し、段階的に切り替える。

### 3.4 段階2・3で検討が必要なこと

| 項目 | 内容 |
|---|---|
| データの出典と権利 | カード名・画像の扱い、Wikiの取得頻度・利用条件の確認。画像は公式へのリンクにとどめるのが安全 |
| 個人情報 | 申請者名などを扱うため、プライバシーポリシーが必要。公開ページでは申請者名を伏せる |
| 費用 | Supabase・Vercel の無料枠を超える可能性。利用量（行数・画像容量・転送量）の監視 |
| 悪用対策 | リクエストの連投防止（回数制限・CAPTCHA）、公開ページの不適切な内容への対応 |
| 管理画面 | 全ショップを横断して見る運営者用の画面（段階3） |

### 3.5 進め方の提案

1. まず **§1 の A1〜A3（安全性・再現性）** を片付ける。拡張の土台になる。
2. 次に **B3（製品IDの導入）と B1（在庫履歴のDB側記録）** を行う。段階2のデータ設計と方向が同じなので、手戻りが少ない。
3. 実際に使いたい人がいれば **段階1（共同管理）** を先に作り、役割とRLSの仕組みを固める。
4. 段階2は、カタログと在庫の分割を「新しいテーブルを作って移行する」形で進め、一定期間は旧テーブルと並行稼働させる。
