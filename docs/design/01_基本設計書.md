## 1. システムの目的と範囲

### 1.1 目的
個人が所有する遊戯王カード（およびスリーブ・プレイマット等のサプライ）の在庫を管理し、友人に在庫を公開して「この カードを譲ってほしい」というリクエストを受け付けるためのWebシステム。

### 1.2 範囲
| 対象 | 対象外 |
|---|---|
| カード・サプライの在庫管理（登録・増減・検索） | 決済・配送 |
| 製品（パック）マスタ管理 | 複数オーナーの在庫管理（[05](05_改善提案とロードマップ.md) で検討） |
| 友人からのリクエスト受付と処理 | 相場・価格の自動取得 |
| 遊戯王カードWikiからのカードリスト取込 | |
| 在庫変更履歴、お知らせ、Discord通知 | |
| バックアップ・復元 | |

## 2. 利用者と権限

| 利用者 | 認証 | できること |
|---|---|---|
| ゲスト（友人など） | **有効な招待リンク**（ログイン不要） | 在庫一覧・サプライの閲覧、リクエストの送信、**自分のリクエストの編集（編集用リンクを持つ場合・受付中のみ）** |
| 管理者（オーナー） | Supabase Auth（メール＋パスワード） | 全機能。在庫の増減・登録・削除、リクエストの処理、マスタ管理、取込、設定、バックアップ、招待リンクの発行 |

- **サイトは招待制**（2026-10-30〜）。招待リンク（`/?invite=コード`）を持たない人は、ログイン画面以外を利用できない。招待リンクの有効期間は 1日・1週間・2週間・3週間・4週間から選び、延長・取り消しができる。
- 招待コードの検証は **DB側（RLS・DB関数）** で行うため、画面を経由せずにDBへアクセスしても閲覧できない。

- 管理者アカウントは Supabase のダッシュボードで作成する（アプリにサインアップ機能はない）。
- **ログイン済み＝管理者** という単純なモデル。ロールの区別はない。
- 画面の出し分けはブラウザ側で `isAdmin` を見て行っているだけで、**実際の保護はDB側の RLS・権限設定・DB関数内のチェックが担う**（[02 詳細設計書 §4](02_詳細設計書.md#4-セキュリティ設計) 参照）。

## 3. システム構成

```
 ┌────────────┐      HTTPS       ┌────────────────────────┐
 │ ブラウザ     │ ───────────────▶ │ Vercel                  │
 │ (React)     │ ◀─────────────── │ Next.js 14 (App Router) │
 └─────┬──────┘                  │  ・画面配信              │
       │                          │  ・/api/scrape（取込）   │──▶ 遊戯王カードWiki
       │ supabase-js（HTTPS）      └────────────────────────┘
       ▼
 ┌──────────────────────────────────────┐
 │ Supabase                              │
 │  ・PostgreSQL（テーブル・RPC・トリガー） │
 │  ・Auth（管理者ログイン）               │
 │  ・Storage（サプライ画像: supply-images）│
 └──────────────────────────────────────┘
       ▲
       │ Webhook（リクエスト受信時）
 ┌─────┴──────┐
 │ Discord     │
 └────────────┘
```

- **アプリケーションサーバーを持たない構成**。画面はブラウザから直接 Supabase（PostgREST）へアクセスする。
- 複数の更新をまとめて行う処理や、権限チェックが必要な処理は **PostgreSQL のDB関数（RPC）** に実装している。
- サーバー側で動くのは `/api/scrape`（Wikiの取得とHTML解析）だけ。

## 6. データ概要

| データ | テーブル | 概要 |
|---|---|---|
| カード在庫 | `items` | 1行＝1つの「カード名×型番×レアリティ×収録パック」と在庫数 |
| 製品（パック） | `products` | パック名（主キー）・発売日 |
| サプライ | `supplies` | スリーブ・プレイマット等と在庫数・画像 |
| リクエスト | `requests` / `request_items` / `request_edit_logs` | 申請本体・明細（カードまたはサプライ）・編集履歴 |
| 在庫履歴 | `stock_logs` | 在庫が変わるたびに増減数と変更後在庫を記録 |
| お知らせ | `news` | ダッシュボードの掲示 |
| 設定 | `config` | キーと値（JSON）の形式。レアリティ順・シーズン・システム情報・Discord Webhook URL |

詳細は [02 詳細設計書 §3](02_詳細設計書.md#3-データベース設計)。

## 8. 非機能要件（現状）

| 項目 | 現状 |
|---|---|
| データ規模 | カード約3.2万件、製品約520件（2026-10時点） |
| 性能 | 検索・並び替え・ページングはDB関数 `search_items` でサーバー側処理。1ページ50件 |
| 同時更新 | 在庫の増減はDB関数でアトミックに加算（連打・同時操作でずれない） |
| セキュリティ | 閲覧は管理者または有効な招待リンクのみ（DB側で検証）。書き込みはログイン必須（RLS・権限）。申請者の編集は編集用トークンでDB側照合。検索エンジンには登録させない（`robots`） |
| 可用性 | Vercel・Supabase のサービス水準に依存。冗長化なし |
| バックアップ | 設定画面からJSON形式で手動エクスポート（自動バックアップなし） |
| ブラウザ対応 | PC（表形式）・スマホ（カード形式）のレスポンシブ表示 |

## 9. 設計上の主要な判断

| 判断 | 理由 | 留意点 |
|---|---|---|
| 検索用の正規化キー列 `search_key`（生成列）をDBに持つ | ひらがな/カタカナ・全角/半角・記号・空白の表記ゆれを、保存データを書き換えずに吸収するため | 正規化規則を変えたら全行の再計算が必要（[04 運用手順書](04_運用手順書.md)） |
| 保存するカード名はひらがなを変換しない（`normalizeForStorage`） | 過去にカタカナ化して保存し、カード名を壊した不具合があったため | 比較・検索用の変換（`toSearchKey`）と保存用の正規化を混同しないこと |
| 申請者の本人確認は編集用リンク（トークン）方式 | ログイン不要のまま、他人による編集を防ぐため | トークンは完了・キャンセル時に入れ替わり、リンクは無効になる |
| 書き込み系の複合処理はDB関数に実装 | 1回の通信でまとめて実行し、途中失敗による不整合を防ぐため | DB関数の変更はアプリのデプロイとは別に SQL の実行が必要 |
