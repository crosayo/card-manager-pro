## 2. 開発環境の準備

```powershell
git clone https://github.com/crosayo/card-manager-pro.git
cd card-manager-pro
npm install
```

`.env.local` を作成する（値は Supabase の Project Settings → API）:

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=（anon public キー）
```

```powershell
npm run dev     # http://localhost:3000
npm run build   # 型チェック＋本番ビルド（コミット前に必ず通す）
```

> `.env.local` は Git 管理外。`service_role` キーは絶対に置かない。

## 3. 改修の流れ

1. `main` から作業ブランチを作る。
2. 修正し、`npm run build` が通ることを確認する。
3. **DB変更がある場合**は、SQLを `src/views/SettingsView.tsx` の `INITIAL_SCHEMA_SQL` に追記し、さらに**単体のSQLファイルとしても用意**する（§4）。
4. コミット → `main` に取り込み → push（Vercel が自動デプロイ）。
5. [03 改修ログ](03_改修ログ.md) に追記する。

---

## 4. DB変更（SQL）の反映手順

### 4.1 手順
1. Supabase ダッシュボード → SQL Editor を開く。
2. **ローカルのSQLファイル（または手元のソース）からコピー**して実行する。
3. 「Success」を確認後、匿名キーで動作確認する（§7）。

> ⚠️ **公開中のアプリの設定画面からSQLをコピーしないこと。** 設定画面のSQLはデプロイ済みの版の内容なので、新しい改修のSQLはまだ含まれていない（2026-10-29 に実際に発生）。

### 4.2 SQLとデプロイの順番
改修ごとに「どちらを先にするか」を決めて、改修ログに書く。

| 状況 | 先にやること |
|---|---|
| 新アプリが新しいDB関数・列を使う | **SQLが先**（後方互換のある関数追加なら旧アプリも動く） |
| SQLで旧アプリが使っている権限や関数を消す | **デプロイが先** |
| セキュリティ修正（権限の取り消し） | できるだけ早くSQLを実行 |

### 4.3 SQLの書き方
- 何度実行しても壊れないように書く（`create or replace`、`if not exists`、`drop … if exists`）。
- 関数の引数を変えるときは、旧シグネチャを `drop function if exists` で消す（残すとオーバーロードになり PostgREST が呼び分けに失敗する）。
- SECURITY DEFINER 関数は、関数内で権限・入力を検証し、`set search_path = public` を付ける。

## 5. 新しい環境を一から作る場合

> ⚠️ 現状、**アプリ内のSQL（設定画面）だけでは全テーブルを作れない**。`requests` / `request_items` / `request_edit_logs` / `supplies` / `stock_logs` の CREATE 文は、ワークスペース直下の旧指示書 `指示書_フェーズ2_履歴とリクエスト機能.md`（タスク8）にしかない。スキーマの一本化は [05](05_改善提案とロードマップ.md) の優先項目。

1. Supabase で新規プロジェクトを作成する。
2. SQL Editor で、次の順に実行する。
   1. 設定画面SQLの 1〜9（items / products / news / config、RLS、トリガー、基本RPC）
   2. 旧指示書フェーズ2 のタスク8（supplies → stock_logs → requests → request_items → request_edit_logs の順。外部キーの依存関係のため）
   3. 設定画面SQLの 10〜14（検索・サプライ在庫・リクエスト関数・権限・トリガー）
3. Storage に公開バケット `supply-images` を作る（旧指示書フェーズ3 タスク15）。
4. Authentication → Users で管理者ユーザーを作る。
5. Vercel にリポジトリを接続し、環境変数（§2）を設定してデプロイする。
6. 設定画面の「バックアップを復元」で、JSONからデータを戻す（製品・カードのみ。リクエスト・サプライ・履歴はバックアップ対象外）。

## 6. 日常運用

### 6.1 バックアップ
- 設定画面 →「バックアップ（Export）」で `backup_YYYY-MM-DD.json` を保存する（**製品とカードのみ**）。
- 大きな改修・SQL実行の前には必ず取る。
- 復元は「バックアップを復元（Import）」。IDが一致するカードは上書きされる。

### 6.2 管理者の追加・パスワード変更
Supabase → Authentication → Users。ログインできる人は全員が管理者になる点に注意。

### 6.3 Wiki取込
`/scraper` に遊戯王カードWikiのパックページURLを入れて取り込む。取込前に内容を確認・修正できる。

### 6.4 招待リンクの発行
- `/invites`（サイドバー「招待リンク」）で、渡す相手のメモと有効期間（1日〜4週間）を選んで発行する。リンクは自動でコピーされる。
- 期限が近いものは「延長」、渡し間違えたものは「取り消す」（その時点でアクセス不可）。
- 一覧の「最終アクセス」「回数」で、実際に使われているかを確認できる。
- 招待リンクが切れると、申請者は自分のリクエストの編集用リンクも使えなくなる（編集用リンクの前に招待リンクが必要）。

### 6.5 リクエスト対応
`/requests` で単価を入れて「完了にする」と在庫が自動で減る。申請者が編集用リンクをなくした場合は、受付中なら管理者が「編集用リンクをコピー」で再送できる。

## 7. 動作確認（匿名キーでの確認例）

PowerShell（`.env.local` の値を使用）:

```powershell
$h = @('-H', "apikey: $key", '-H', "Authorization: Bearer $key", '-H', 'Content-Type: application/json')
# 検索（ひらがな・空白）
curl.exe -s -X POST "$url/rest/v1/rpc/search_items" @h --data-binary '@body.json'   # {"p_search":"青眼の白龍","p_page_size":3}
# 権限の拒否（42501 が返れば正常）
curl.exe -s -X POST "$url/rest/v1/rpc/increment_stock" @h -d '{"item_id":-1,"delta":0}'
curl.exe -s "$url/rest/v1/requests?select=token&limit=1" @h
```

> 日本語を含むJSONはファイルに UTF-8（BOMなし）で保存して `--data-binary @ファイル` で送る（PowerShell の直接指定は文字化けする）。
> データ全削除の関数 `reset_all_data` は、確認目的でも匿名で呼ばないこと。

## 8. よくあるトラブル

| 症状 | 原因と対処 |
|---|---|
| 検索が遅い／全件読み込みになる | `search_items` が未登録（ブラウザのコンソールに警告）。設定画面SQL 10〜11 を実行 |
| `PGRST202`（関数が見つからない） | SQL未実行、または引数名の不一致。旧シグネチャが残っていないかも確認 |
| `permission denied for table requests` | anon で `token` 列を含めて取得している。列を明示する |
| ひらがなのカード名がカタカナになった | 保存経路で `normalizeCardName`（比較用）を使っている。`normalizeForStorage` を使う |
| `git push` で認証エラー | Git Credential Manager の認証切れ。`git push` を手動実行してブラウザで再認証 |
| 一括置換スクリプトで一致しない | 作業ツリーの改行コードが CRLF（`core.autocrlf=true`） |
| 正規化規則を変えたのに検索結果が変わらない | `search_key` は行の更新時にしか再計算されない。`update public.items set name = name;` |
